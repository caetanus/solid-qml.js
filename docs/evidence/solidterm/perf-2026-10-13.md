# SolidTerm performance: measurements, profile, fixes (2026-10-13)

Branch `st-perf` (from `widgets` 7205a13). Bench: `scripts/solidterm-bench.sh <binary> <label> [cases]`
(inputs from `scripts/solidterm-bench-gen.py`, report from `scripts/solidterm-bench-report.py`,
parity screen from `scripts/solidterm-parity.sh`). Every number below is the median of 5 runs (p95
in the tables), taken with the 1-min load average under 2 (the max seen is in the tables).

## Setup and one caveat about "the real display"

- GPU/driver (QSG_INFO): `OpenGL VENDOR: Intel RENDERER: Mesa Intel(R) UHD Graphics 630 (CFL GT2)
  VERSION: 4.6 Mesa 26.2.2`, **threaded** render loop, vsync 16.67 ms.
- The owner's session was locked with the output powered off (swayidle DPMS) during the whole
  run. With the output off, sway sends no `wl_surface.frame` callbacks, so QtWayland logs
  "Didn't receive frame callback in time, window should now be inexposed" and Qt Quick renders
  **nothing**. A first seq run on `wayland-1` produced 0 frames in 53 s. That shows how Wayland
  behaves with the output off. It is not a SolidTerm bug.
- So every run used a **headless sway on the same Intel GPU** (`WLR_BACKENDS=headless`,
  `WLR_RENDER_DRM_DEVICE=/dev/dri/renderD128`, output 1896x2020@60 Hz at scale 2, so the window gets
  the owner's logical 948x1010 half-screen and DPR 2). Client rendering is real GL on the iGPU (the
  glyph material renders; it does not fall back to software), and frame callbacks pace at 60 Hz.
  Scanout to the panel is the only thing missing. The owner's config was used unchanged
  (NotoMono Nerd Font 15 px, opacity 81, monokai, scrollback 8000). The compositor-side blur is
  inert there, and it costs nothing on the client.
- Grid: SolidTerm 105x56. Tilix (VTE, `--new-process`, floating) came up at 118x57 whatever
  `--geometry` asked for, so it has **14% more cells** than SolidTerm, which counts against Tilix.
  xterm was not compared: the headless sway's XWayland display could not be told apart from the
  owner's.
- Throughput is timed inside the terminal: `date +%s%N` before and after the command. The command
  returns once the terminal has consumed its output (pty back-pressure). CPU comes from sampling
  `/proc/<pid>/task/*/stat` every 50 ms and is split into the main (GUI) thread and
  QSGRenderThread.

## Profile findings (perf record -g, frame-pointer release build, headless GPU sway)

Each suspect from the brief, confirmed or refuted with data:

1. **QML property-change storm: CONFIRMED, the biggest SolidTerm-side cost. Fixed.** Every line
   pushed to the scrollback emitted `scrollChanged()`. The composed QML scrollbar re-evaluated
   its bindings and ran its `pulse()` handler for every line, which was 26.4% of the GUI thread
   (`QQmlNotifier::emitNotify`) in seq. After the fix it is 0.25%.
2. **Per-cursor-move work: CONFIRMED (3.5%). Fixed.** `cbMoveCursor` → `resetBlink()` restarted
   the blink QTimer and called update() for every cursor move.
3. **libvterm's own screen model: CONFIRMED, now the wall (architectural, see P1).** After fixes
   1 and 2, `vterm_scroll_rect` is **86.8% of all samples** in seq. Of that, libc memmove is about
   65%: libvterm's `moverect_internal` memmoves the whole cell buffer, 105x56x36 B ≈ 208 KB, on
   **every** scrolled line. `vterm_screen_get_cell` copying each row out for `sb_pushline` is about
   14%, and our push copy was 6.75%. The dense case has no scrolling and SolidTerm beats Tilix
   7x there. In the scroll cases (seq, mixed, region) libvterm's O(screen) scroll is what loses.
4. **Per-cell allocations in the grid build: CONFIRMED. Fixed.** One QString per cell (two heap
   allocations), a QString hash per cell, and three vertex vectors regrown every frame.
5. **Atlas re-upload: CONFIRMED, but a one-off.** Any new glyph re-uploads the whole 2048²
   RGBA atlas (16 MB) through `createTextureFromImage`. The first glyph burst (with the first
   bold/italic font load) costs one ~64 ms updatePaintNode, and that happens while the GUI thread
   is blocked. Steady state never re-uploads. Not fixed here; see P3.
6. **Small pty reads / per-chunk synchronous processing: REFUTED as a cost.** Reads are 4 KiB
   (pty_reads 3026 for 12.4 MB). After the batching fix, everything in the read path outside
   `vterm_input_write` is 0.4% of samples, so read-until-EAGAIN with bigger buffers would save
   <0.5%. Each read already ends in one update(). Frames keep a steady 60 Hz during floods
   because each read takes milliseconds, not seconds, so the GUI thread syncs every frame.
7. **update() not coalesced: REFUTED.** QQuickItem::update() is idempotent per frame, at 0.33%
   (`cbDamage` now skips it inside a batch anyway). Rendering is one updatePaintNode per vsync
   (62 fps measured).
8. **Full-grid geometry rebuild every frame: CONFIRMED but cheap.** It is 0.18–0.99 ms per frame
   after fix 4, versus a 16.7 ms budget. Incremental, dirty-row geometry would save at most
   ~1 ms per frame in the dense case. Not worth its complexity yet (P4).
9. **Render loop / vsync: fine.** The loop is threaded, and the render thread is 3–15% of a core.
   Frames are vsync-paced at a stable 16.0–16.2 ms.
10. **Text shaping per frame: REFUTED.** Glyphs are rasterised once into the atlas. No shaping
    shows up per frame.
11. **Blur/translucency:** the blur is compositor-side (ext-background-effect), with zero client
    cost. Translucency is one extra full-size quad.

## Architectural proposals (NOT implemented: owner decides)

**P1. Own screen buffer on top of libvterm's state layer (replaces `VTermScreen`).** Keep
libvterm's parser and `VTermState` (escape handling, modes, pen, charsets) and implement
`VTermStateCallbacks` (putglyph / scrollrect / moverect / erase / setpenattr …) into our own grid:
rows held as a ring of row pointers. A full-screen scroll then rotates an index, O(1), instead of
memmoving 208 KB, and a line scrolled into the scrollback is handed over as a row buffer, with no
per-cell `vterm_screen_get_cell` copy. Measured stake: 86.8% of seq's samples sit in
`vterm_scroll_rect` (memmove ~65% + get_cell ~14% + push ~7%). Expected: seq from 33 s to roughly
4–7 s and mixed from 12 s to roughly 3–5 s, which is Tilix territory (3.1 s / 4.2 s), with dense
staying 7x ahead of Tilix. Cost: we take over damage tracking, alt-screen, resize/reflow and
selection/search/link reads (all of them read cells today). It is a sizeable but contained
rewrite of `TerminalView`'s data side. The renderer would read our rows directly, which also
removes `vterm_screen_get_cell` from updatePaintNode.

**P2. Parser off the GUI thread** (feed libvterm, or the P1 grid, on a worker and publish
snapshots/damage). In every flood the GUI thread is at 100% of a core, so it would decouple input
and QML responsiveness from output floods. It brings locking or double-buffering of the grid into
the sync. Do it only after P1: P1 removes most of the work this would move.

**P3. Partial atlas uploads** (a custom QSGTexture that keeps its QRhiTexture and uploads only the
dirty sub-rectangle through `QRhiResourceUpdateBatch::uploadTexture`). It removes the 16 MB
whole-atlas re-upload behind the one-off ~64 ms stall. This is a new technique here (QRhi
resource batches), so it gets explained first per the owner's rule.

**P4. Incremental geometry** (re-emit only damaged rows into persistent vertex buffers). It saves
≤1 ms per frame at most, so it has low priority.

## P1: own screen buffer (branch `st-buffer`, implemented)

Design: `docs/solidterm-screen-buffer.md`. `VTermScreen` is gone. `TermScreen` implements
`VTermStateCallbacks` on a table of row handles: scrolls move handles, and a row leaving the top
is moved (not copied) into a recycling scrollback ring. Same harness as above (headless sway on
the same Intel GPU, owner config, 105x56, 5 runs each, median (p95)). The baseline was re-measured
in the same session: `963ee24` built with the same options (release, `qml_debug=false`).

| case | SolidTerm 963ee24 | after `415a842` (own buffer) | after `4acb4db` (+ erase fix) | Tilix 0.9 / VTE |
|---|---|---|---|---|
| `seq 1 5000000` | 33.97 s (38.90) | 3.69 s (3.83) | **2.81 s** (2.83), **−92%** | 3.29 s (3.40) |
| `cat` 100 MB mixed | 11.87 s (12.02) | 4.16 s (4.28) | **3.69 s** (3.84), **−69%** ¹ | 4.27 s (4.48) |
| dense cells, 50 MB | 0.66 s (0.71) | 0.62 s (0.71) | **0.55 s** (0.80) | 2.88 s (3.31) |
| scrolling region, 50 MB | 3.95 s (3.98) | 1.62 s (1.71) | **1.53 s** (1.66), **−61%** | 2.27 s (2.38) |
| CPU during output (main / render) | 95–98% / 3–15% | 94–98% / 3–15% | 94–97% / 4–14% | 91–96% |
| idle CPU (10 s) | 0% | 0% | 0% | 0% |

The targets were seq ≤ 7 s and mixed ≤ 5 s. SolidTerm now beats Tilix in all four throughput
cases (Tilix also has 14% more cells, 118x57). The main thread is still saturated during a flood,
so throughput is now bound by libvterm's parser plus our glyph writes (see the profile below).

¹ 4 of 5 runs. The 5th run (mixed, run 4 of the final bench) timed out at 300 s with no timing
written: `cat` never finished, so the terminal stopped consuming the pty mid-stream. The cause
could not be reproduced. 90 targeted repeats of the same case on the live headless GPU (40 with
the perf probes on, exactly like the bench) all finished in about 3.5 s. Replaying the exact bench
inputs (mixed, dense, region; random 1–64 KiB chunk boundaries) through both the old and the new
path headless ends in identical screens and scrollback, with no stall. The ~160 bench runs of this
session had no other failure (baseline included). This stays an open risk; see the report.

Frames (the measured interval): seq / mixed / dense / region / wheel stay at 62–64 fps, with 0–0.5%
of intervals over 16.7 ms, as before. updatePaintNode average: seq 0.18 → 0.15 ms, dense 0.92 →
0.83 ms, region 0.49 → 0.45 ms. Mixed 0.40 → 0.52 ms is the same one-off ~64 ms first-glyph atlas
upload (P3, untouched here) spread over 3x fewer frames, because the run is 3x shorter.

Input latency (300 keys, `bash --norc`), median (p95): key → finished geometry 1.04 (1.34) →
**0.85 (1.04) ms**; key → frameSwapped 3.72 (4.15) → **3.70 (4.14) ms**. No regression.

### Profile after P1 (perf, frame-pointer build, seq)

With the own buffer alone, `seq` had a new hot spot: `TermScreen::eraseInternal`, 48% of samples.
That is the erase of the row that comes in at the bottom on every scrolled line. The per-cell
store reloaded the template cell's bitfield word every iteration (the compiler cannot prove the row
does not alias it) and stalled on store forwarding, at ~4.6 ns per 36-byte cell. `4acb4db` writes
the first cell and fills the rest with doubling `memcpy`. A headless 2M-line micro-bench went from
708 to 490 ns per line (340 ns with the scrollback off; the difference is the cold recycled row),
and the live seq from 3.69 s to 2.81 s. After that, no single symbol is above 10%: `putglyph`
~10%, libvterm's parser spread over many small functions, libc copies, `moveRect`/`pushRow` ~2%
each. `vterm_scroll_rect` (86.8% before) no longer exists in the profile.
